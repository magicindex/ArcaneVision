# P1 实测：ext4 裸设备读取器

验证日期：2026-11-02（Asia/Shanghai）
对象：`/dev/dm-1`（LVM → ext4，挂载于 `/vol1`）

## 结论

裸设备读取器与内核 `getdents64` 结果**逐路径一致**。全卷 3,688,330 条记录中，与 `find -xdev` 的差异 2,361 条，全部发生在两次扫描之间：2,357 条在 `/vol1/docker`（容器运行中创建/删除），2 条是扫描期间新写入的测试文件，2 条是微信备份库轮转的 `-shm/-wal`。

`/vol1/1000`（642,823 条）与 `/vol1/@appcenter`（208,504 条）两个子树的条目数与 `find` **完全相等**。

## 关键实现点

1. **inode 位图是唯一权威**。ext4 inode 表在已释放槽位会残留旧数据：按 `mode != 0` 判定会扫出 847 万"inode"（实际已用仅 357 万），其中约 71 万个假"目录"会让 extent 解析随机失败。改为读每组 `bg_inode_bitmap`（每块 4096 位）后，目录数落到真实的 47.6 万。
2. **只读组内已初始化前缀**。按 `bg_itable_unused` 截断，跳过 `INODE_UNINIT` 组，inode 表读取量从 15.6 GB（61,046,784 × 256 B）降到约 0.9 GB。
3. **extent 树在内存里展开**，得到 (物理块号, 目录 inode) 列表；以 `i_size` 作块数预算，兼容未初始化 extent（`ee_len > 32768`）。
4. **按物理块号排序后合并连续块**，单次最多 1 MB 顺序读，把 49 万个目录块的随机读压成少量大读。
5. **目录项解析**按 `ext4_dir_entry_2`：`inode u32 / rec_len u16 / name_len u8 / file_type u8`，跳过 `.` 与 `..`，`file_type=7` 记为符号链接；htree 目录的 dx_root 伪目录项（inode 0）自然跳过，叶子块照常解析。
6. **DFS 先序还原**：边按父 inode 排序后二分定位子区间，根 inode 2，记录编号与 `getdents` 先序一致，路径可由 parent 链单向上溯。
