# 玄览 架构说明书

## 1. 目标与约束

- 目标：在飞牛 fnOS（Debian 12，ext4/ZFS 混合卷）上，对百万到千万级文件提供毫秒级名字检索。
- 约束：ext4 没有 MFT、没有 USN Journal，内核只提供目录遍历与 fanotify；单盘 HDD 的随机读 IOPS 是硬上限。
- 非目标：内容全文检索（那是 Recoll 的领域）；Windows/NTFS 之外的专有文件系统。

## 2. 数据流

```
            ┌────────────┐    xl_store     ┌────────────┐   xl_index   ┌──────────────┐
 目录树 ──▶ │  scan.c    │ ─────────────▶ │  index.c   │ ───────────▶ │ snapshot.c   │ ──▶ 单文件
            │ getdents64 │  recs + names  │ trigram    │  ids/ranges  │ 4KB 对齐段    │
            └────────────┘                └────────────┘              └──────────────┘
                                                                              │ mmap
                                                                              ▼
                                                                     ┌──────────────┐
                                                              查询 ◀──│  query.c     │
                                                                     └──────────────┘
```

扫描与查询完全解耦：扫描是一次性的批处理，查询只碰 mmap 的只读页面，不需要任何进程间拷贝。

## 3. 记录模型

```c
typedef struct {          /* 20 字节，定长数组 */
    uint32_t parent;      /* 父记录号；根记录为 XL_ROOT */
    uint32_t name_off;    /* 名字池偏移 */
    uint32_t size;        /* 低 32 位，--stat 时才填 */
    uint32_t mtime;       /* 秒，--stat 时才填 */
    uint16_t name_len;
    uint8_t  flags;       /* bit0 目录，bit1 符号链接 */
    uint8_t  reserved;
} xl_rec;
```

只存最后一段名字，路径靠 parent 链上溯拼接。这样 700 万条记录约 140 MB，
而存全路径要 3–5 倍。代价是每次输出要走上溯（深度一般 < 10，可忽略）。

`size/mtime` 默认不填：默认扫描不调用 `stat`，省掉每条一次系统调用；
结果页需要时再 `stat` 前 50 个即可。`--stat` 可以打开，代价是扫描变慢。

## 4. 快照格式

128 字节定长头 + 各段 4KB 对齐：

| 段 | 内容 | 说明 |
|---|---|---|
| header | `xl_hdr` | magic `XLANIDX`、版本、各段偏移与长度 |
| records | `xl_rec[]` | 20B × N |
| names | 字节池 | 名字首尾相接，无分隔符，靠 `name_off/name_len` 定位 |
| tri_ids | `uint32[]` | **只存出现过的** trigram，升序 |
| tri_ranges | `{off,count}[]` | 指向 postings 段的字节偏移与条目数 |
| postings | 块序列 | 定宽位打包 |
| root | 字符串 | 扫描根，用于还原绝对路径 |

加载 = `mmap` + 校验 magic/版本/长度，没有任何反序列化。这就是"重启即用"：
进程起来指针一挂就能查，不需要把 400 MB 读进堆。

稀疏表而不是 2^24 全表：全表 `{off,count}` 要 134 MB，稀疏表按实际出现的
（通常 200 万–400 万）只占十几到几十 MB；代价是二分查找，约 20 步、百纳秒级。

## 5. 倒排编码

每个 trigram 的 id 序列按 128 条分块：

```
block = [ u32 base ][ u16 n ][ u8 bits ][ u8 pad ][ n-1 个 delta，定宽位流 ]
```

- 块内 id 升序，存的是相对前一条的 delta；
- `bits` 由块内最大 delta 决定，块与块独立；
- 实测 1.29 B/posting（定宽 uint32 要 4 B，变长编码约 1.1–1.5 B 但随机访问要线性解码）。

选位打包而不是变长编码，是因为查询要做**游标式跳过求交**：块头自带 base，
可以直接跳到目标块，而不必从头解码整段。块尺寸 128 是压缩率与跳过粒度的折中。

## 6. 查询

三条路径：

1. **长度 ≥ 3**：对查询串取所有 trigram，查稀疏表取 count 最小的一个作为候选源（稀有优先），
   遍历它解出的 id，对每条做整名子的逐字节复核（ASCII 折叠），通过即命中。
2. **长度 1–2**：没有 trigram 可用，直接在名字池上做大小写不敏感的子串扫描，
   命中偏移二分回落到记录，再复核。P0 的权宜之计：173k 条时 18 ms，700 万条时约需 0.7 s，
   P1 会用前缀/首双字索引替掉。
3. **命中不存在**：任一 trigram 计数为 0 即直接返回空，不做遍历。

结果按 `mtime` 降序、再按名字长度排序。收集上限为 `max(1000, 50 × N)`：
超过上限时标记 `truncated`，输出 `>=N`。理由是单字符这类查询可能命中百万条，
全量收集既慢又无意义；先按 DFS 序截断，近似等价于"浅层优先"。

## 7. 扫描

`getdents64` + DFS 先序递归，`d_type` 直接给出文件类型，默认不 `stat`。
先序保证 **子记录编号一定大于父记录编号**，于是：

- 路径还原只朝编号更小的方向走，不会成环；
- 快照不需要任何指针修补，`mmap` 后即是可用结构。

`--exclude` 的目录仍然记录（可被搜到），但不进入其子树。

## 8. 已知限制

| 限制 | 影响 | 计划 |
|---|---|---|
| 建索引时 `postings` 用 uint32 临时数组 | 700 万条约 450 MB 峰值 | P1 改为分段构建 + 直接编码 |
| 短查询走全池扫描 | 千万级时接近秒级 | P1 前缀数组 |
| 单线程扫描 | HDD 冷扫未充分并发 | 实测 2 线程即饱和（RAID1 单盘），暂不并行 |
| 无增量 | 每次全量重建 | P2 fanotify + 对账 |
| 无权限过滤 | 结果不按用户可见性裁剪 | P3 |
| 中文无语义分词 | 只能按字节子串匹配 | 可接受；拼音索引放 P3 |

## 9. 版权与实现边界

- 算法（trigram 倒排、bitpacking、游标求交）是通用技术，本仓库自行实现；
- 未引用、未改编 Everything 或 kerything 的源码；
- 不链接 `libext2fs`（LGPL）：P1 的 ext4 裸设备读取将按公开的 on-disk 格式规范自行实现，
  从而保持全静态、无许可证传染。
